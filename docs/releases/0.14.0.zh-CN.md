## 行为变化

PR #183 已在 `47d8d86b97fb436d4c34e6e2ce5bfffcb7c196e5` 合入主分支，
对应 PR CI `40061289134` 和主分支 CI `40061831926` 均通过。
Core 删除了 Docker/Podman CLI 执行、命令参数构造、端口与 inspect 输出解析。
托管服务必须明确配置 `lifecycle_host`。缺少配置会在分配新租约之前报迁移错误，
插件失败也不会回退旧 CLI。有效的外部服务值继续走原有 recipe 检查。

租约、心跳、并发隔离、持久化日志、恢复协调和最终门禁判定仍由 Core 负责。
插件负责引擎操作。旧租约读取和诊断是恢复边界，不是仍可执行的旧引擎后端。

## 升级步骤

1. 停止使用旧 Core 的并发任务，保留原项目、报告目录、旧租约和诊断证据。
2. 用原批准版本或明确的人工流程核对旧资源的引擎、不可变对象 ID 和所有权标签，
   完成旧资源及占用的处理。引擎不可用、名称不存在或响应不明都不能当作资源已消失。
   不要删除、重命名或移走租约来绕开冲突。
3. 通过受保护的安装流程安装对应引擎插件，配置明确的 `lifecycle_host`。
   Podman 使用 rootless 5.7.0、`podman-lifecycle` 0.3.0 和 lifecycle-v1；
   Docker 还需要独立 `readiness_host`。详见
   [完整迁移边界](../runtime-lifecycle-v1.md#legacy-cli-retirement)。
4. 检查可用性，再执行实际服务验证。新生命周期的恢复继续要求显式 fence、
   reservation/journal 和精确对象身份。不能将旧 lease-v2 文件交给 `lifecycle-cleanup`。

新 Core 的 `cleanup --dry-run` 可以报告保留的旧记录和迁移错误，可能返回非零退出码。
普通 `cleanup` 也不会回收旧容器或删除其标记。本版本不提供旧租约自动接管、
自动删除或全局容器清理命令。回退 Core 二进制不等于回滚资源状态，仍须保证单一操作者。

## 验收范围

退役回归覆盖缺少 host、外部服务配置、旧租约无法被抢占或隐式迁移，
以及 human/JSON cleanup 诊断和引擎 PATH trap。真实引擎候选验收与发布后的
下载验收分别记录，不能将原 Core 0.13.0 的结果直接标记为 0.14.0 通过。

已发布 importer 0.6.0 的 manifest/core pin 声明 Core 0.13.0。
候选测试可以验证其安装描述符与新 Core 的运行兼容性，但不会扩大该不可变发布物的
认证范围；如需正式声明新版本支持，应由 GateProbes 发布新的兼容性记录或版本。
