# Core 0.14.1：协议复用发布修复

状态：未发布候选。保留 Core 0.14.0 的全部退役行为、迁移要求和原始验收身份。

## 保留失败版本

`v0.14.0` 固定在 `c3a79e6b9449c2b9a69ac4480a7ec350c33c1a89`。
发布 run `40072636598` attempt 1 的策略检查与四平台构建成功，但协议发布步骤失败，
后续 quality/GitHub/Core crates.io 发布被跳过。标签不移动、不删除，保护规则不变。

Protocol 0.6.0 已从先前提交发布。Cargo 的 `.cargo_vcs_info.json` 写入打包提交，
后续 Core 提交重新打包时即使协议源码完全不变，也会产生不同的 crate SHA-256。
原脚本把本地归档 SHA 当成 registry 归档 SHA，导致不可复用已发布协议。

## 修复边界

先下载 registry 包，并按 registry metadata 的 checksum 验证其完整性。
完全相同的字节继续直接通过；字节不同时，比较有界归档中的全部普通文件、权限和内容。
拒绝路径穿越、重复条目、非普通文件及超限内容。仅允许有效、干净 VCS 记录中的
`git.sha1` 提交戳不同；`path_in_vcs`、dirty 标记和其他字段仍参与比较。
源码、Cargo.toml、Cargo.toml.orig、Cargo.lock、文件集合和实际权限的变化均拒绝复用。
不覆盖已有协议，不增加或重试任何失败的上传。

## 前置条件与后续验收

Core 升级为 0.14.1，protocol 保持 0.6.0。Onboarding 必须使用声明精确 0.14.1
兼容性的新发布包，不放宽 Core 的精确版本检查。保留原 0.14.0 本地 Podman 和
onboarding 回执，不将它们改名冒充 0.14.1 下载验收。

修复和版本必须经 PR 合并、exact-main CI 通过后才创建新 `v0.14.1`。
按原发布治理进行环境审批、签名及 registry 发布，再对下载的正式 Core 做全新安装、
29 步 onboarding 和真实 rootless Podman 生命周期验收。发布完成前不宣称整体交付完成。
