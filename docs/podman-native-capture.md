# Native Podman capture contract corrections (114)

Wire checkpoint with runner design for independent review; unpublished. Typed wire, request matching and operation-key primitives are implemented; the runner is not. First operation is
read-only image plan capture. No create/start/stop/remove/exec, lease, reservation
or mutation token. Docker v1 and old Podman raw-context records are not accepted.
The existing lifecycle-v2 profile selects the product; the wire envelope uses a
separate exact schema `gate-runtime/podman-capture-v1` to distinguish this limited
entrypoint from a future lifecycle mutation contract. Outer dispatch must match capture-v1 exactly; lifecycle-v2 fallback or schema inference is forbidden.

## Request

Canonical JSON in fixed struct order, no extra whitespace/newline, max 64KiB:
`schema`, `profile`, `invocation`, `image_id`, `inputs`, `timeout_ms`.
Profile is the existing exact podman-lifecycle/0.1.0/lifecycle-v2/podman tuple.
Invocation is 128 fresh random bits generated by Core, 32 lowercase hex chars;
never inferred from env or accepted as a persistent authority. Image is the
exact full native image ID, not tag or name. Inputs reuse PlanInputs preflight.
Timeout is an integer 1..30000 milliseconds. All schemas reject missing, unknown,
duplicate and noncanonical fields. Canonical inputs have fixed name/labels/port
order, sorted label keys, and explicit null for absent port.

## Protected descriptors

Core opens VerifiedPodmanInstallation from an explicit host path. It revalidates
all held bytes, derives identity and original config path, and creates a sealed
Linux memfd for expected inputs. No public request supplies expected identity.
Fd4 expected object: schema `gate-runtime/podman-capture-expected-v1`, invocation,
request_sha256, host_sha256, installation_sha256, config_sha256,
executable_sha256, config_path, operation_key. Fixed order, bounded 16KiB.
Operation key is SHA256 of a canonical typed envelope containing domain
`gate-runtime/podman-capture-key-v1`, exact request digest and the four snapshot
digests. This is binding, not authentication or replay protection. The capture_binding module freezes struct field order and a SHA256 golden vector.

Fd3 is a child-only duplicate of the original held read-only configuration file, positioned independently; the parent retains its original CLOEXEC descriptor unchanged.
fd4 is sealed against write/grow/shrink and further seal changes. Child owns both
inherited descriptors; it marks its owned fd3 CLOEXEC before passing it to
from_held_versioned (exec inheritance necessarily cleared that bit). It checks
fd3 type/mode/link/owner/path identity and exact wrapper digest. It never opens
config_path for data. It validates fd4 seals, owner/type/size and expected schema;
request digest, invocation and operation key must match before any connection.
No installation/host/executable paths are reopened by the adapter. Their digests
are host-bound assertions at this child boundary, not independently verified by
the child. Fd4 is not privileged against another process of the same UID.

Core executes the held executable descriptor; no CLI fallback, PATH search,
ambient environment or implicit socket. Empty environment and cwd `/`; preserve
only declared stdin/stdout/stderr/fd3/fd4 plus the minimum executable FD needed
for held-file spawn. The fixture must exercise actual fd inheritance rather
than relying solely on library callbacks. Executable magic is insufficient ABI
proof: failed spawn/exit/parse must be explicit failure, never capability success.

## Timing, response and persistence

Host uses one absolute monotonic deadline including spawn and I/O, cancellation
and final validation. Child starts its timeout budget on process entry, before
reading stdin/fds; parsing and every GET use the remaining budget. Host timeout
is authoritative and must kill/reap child; no replay/retry. Use bounded reads and
bounded private stdout, no raw configuration on stderr or user diagnostics.

Success stdout is one canonical envelope: schema
`gate-runtime/podman-capture-response-v1`, invocation, operation_key,
request_sha256, record_b64, record_sha256. record_b64 is standard padded canonical base64 of exact canonical PlanRecord bytes. Decoded record is at most 16MiB and whole response at most 24MiB; reject noncanonical base64, oversized decoded bytes, and digest mismatch before parsing the record. Exit0 and empty stderr required.
Failure exits nonzero with no stdout evidence; bounded constant diagnostics only.
No success/failure union that can accidentally turn failure into an accepted plan.

Host validates exact envelope/bindings, record hash and canonical record, explicitly calls match_capture_request for exact image ID and operator name/labels/port, then checks
RecordInstallationMatch against its still-held installation, revalidates all
files and cancellation/deadline. Only then may a separate explicit caller create
an evidence file using create_new. The adapter never chooses or writes an output
path. Record remains non-authoritative; no installation_verified upgrade.
Host response substitution, replayed invocation, malformed record and postresponse
cancel/timeout are all failures. A successful read-only capture is not proof of
current image freshness after return, daemon restart identity or mutation safety.

## Implementation/review gates

Freeze schema/key golden vectors and exact FD/ELF spawn policy first. Add native
fake-socket positive response, inherited-label persistence, fd3/fd4 missing or
wrong-type/ownership/seals, wrong request/identity/hash/profile/invocation,
replacement before and after response, malformed/trailing/oversized input/output,
zero-socket negatives, cancellation/deadline and no retry. Keep protocol crate
unpublished/local-patched until its versioned release is coordinated. No real
engine or daemon changes are part of this contract slice.


## Implemented wire checkpoint (115)

capture_wire now implements canonical typed request and expected envelopes,
request/key matching, and base64 response encode/decode. Limits are 64KiB request,
16KiB expected, 24MiB response, and 16MiB decoded record. Response processing
checks bindings, canonical base64 and SHA256 before PlanRecord parsing, exact
image/operator inputs and installation/config digest comparison. There is no
fallback to lifecycle-v2 outer schema. base64 uses the existing locked 0.23.1
crate; no custom base64 implementation is introduced.

These are pure data APIs. CaptureExpected::bind takes caller assertions and does
not mint trusted fd4 contents. The future Core host must derive them from held
snapshots. FD ownership/seals, executable ABI, process exit/stderr, deadlines,
cancellation and real native spawn remain unimplemented integration gates.

## Protected input parser checkpoint (116)

capture_inputs::parse consumes child-owned config/expected files and bounded
request bytes. It restores CLOEXEC on these owned descriptors, verifies expected
memory is regular, zero-link, euid-owned 0600, 1..16384 bytes, and has all four
write/grow/shrink/seal seals. Positional reading ignores its cursor. Canonical
request/fd4 binding is checked before from_held_versioned consumes fd3; the exact
config wrapper hash must match. The parser opens no config path and performs no
socket connection, though context loading holds the selected socket O_PATH.
Seals prove immutable bytes, not launcher authentication. The future child must
supply actual inherited fd3/fd4; this API alone cannot prove descriptor numbers,
parent provenance, process deadline, stderr/exit handling or real engine identity.

## Core host source checkpoint (118)

The internal podman_capture_host runner now mints a fresh 128-bit invocation,
derives expected hashes/config path from a live installation, stages its original
config descriptor with sealed expected bytes, and executes the held executable
via procfd. It reuses only fd_inputs and raw_adapter transport/supervision, with
empty env, cwd `/`, exact stdin, bounded stdout/stderr, process exit checks and
final record/request/installation/cancel/deadline validation. No Docker wire,
journal or lease module is used. with_held_config is an additive generic FD
transport primitive; existing sealed-config callers are unchanged.

This source checkpoint needs native positive and kill/reap/signal/output-limit
joint tests before host acceptance. It is not a public ServiceManager route,
fixed Core-owned host mapping, published protocol or installed product. New
source is registered to the same process quality owner/risk series; the broader
unpublished Podman series still needs release-wide quality inventories and CI.

Checkpoint 119 adds a second live record/installation revalidation after the final
cancel/deadline callback and immediately before return. This catches changes made
during that callback; it does not provide atomic exclusion against same-UID
changes after the final check. Direct original-config FD tests cover child bytes,
parent flags/bytes, closure-owned descriptor release, reserved target holes and
swapped source allocation. They exercise generic FD staging only; positive Core
capture and process supervision joints are still required.

Checkpoint 120 adds a final cancel/deadline check after the last installation
revalidation, so revalidation time is charged before success. An internal no-op
observer permits deterministic tests after that exact boundary; production
callers cannot supply it. A dedicated opt-in podman-capture-joint-tests feature
requires HG_PODMAN_NATIVE_BINARY and HG_PODMAN_NATIVE_SHA256 and fails if absent.
It copies the exact hashed native ELF into a protected installation fixture,
executes through the Core held-procfd runner, and checks three fake GETs plus
record persist/reopen/live match. Separate final-boundary tests cancel or consume
the budget after revalidation and require rejection. No real engine is used.
Signal, TERM-resistant timeout/kill-reap, blocked stdout/stderr/oversize and
partial-output discard tests remain required.

Checkpoint 121 adds deterministic final-observer same-byte executable replacement
and revalidates immediately after that observer. A separately compiled, hashed
Rust ELF fixture exercises partial stdout/nonzero exit, stderr, over-24MiB stdout,
and a TERM-resistant child. Tests require failure, zero socket connects, bounded
return and ESRCH for the direct child PID after host return. The fixture is
explicit test source and never linked into production. These tests do not yet
cover actual adapter SIGTERM/SIGINT during all three I/O phases, full stderr,
blocked output below the cap, descendant reaping or arbitrary same-UID mutation
after the final check. They do not establish real engine behavior.

## Project mapping checkpoint 126

Core's internal `capture_installed(Project, image_id, inputs, timeout, cancelled)`
selects exactly `.harness-gate/runtime/podman-capture-v1/host.json` under the
canonical absolute project root. No caller host path, environment lookup,
default socket, alternate product or fallback is accepted at this entry.
The existing held loader validates the protected host and its referenced members;
installation/config/executable paths remain explicit descriptor fields, not
required to reside beneath the project. The project selects the configuration;
this mapping is not signed distribution trust or authentication.

The call returns only a validated PlanRecord. It creates no directory, record,
lease, reservation or mutation. The caller may separately use create_new, with
its existing evidence-only and same-context limitations. Fake-native tests cover
mapped capture, separate explicit persistence, missing mapped host despite a
valid host elsewhere, and symlink refusal with zero socket connections.

This is an internal mapping API, not a CLI or ServiceManager route. The native
binary still requires the pinned local protocol source. No real Podman socket,
installed release, public command, restart or rootless acceptance is claimed.
Protected installation loading precedes the runner's request budget; filesystem
work is not preempted. This does not strengthen the previously documented
same-UID race or process-containment guarantees.


## Explicit host trust-root policy (checkpoint 127)

The fixed project host.json is an operator-selected configuration trust root.
Its installation/config references may point outside the project; confinement to
project descendants is deliberately not the policy. The host binds exact hashes,
and every external member still passes the existing ownership, permissions,
canonical-path, held-file and revalidation checks. Tests use a separate protected
installation tree and reject a changed executable digest and a group/world-writable
executable before connecting. No discovery or fallback is introduced.

Selecting a Project does not authenticate that project. A caller must explicitly
trust the selected project and its host configuration before invoking this internal
API: loading host.json may launch its declared executable. A malicious same-UID
operator can author a different self-consistent descriptor and executable; hashes
are not signatures or an executable allowlist. Do not automatically invoke capture
while opening or inspecting an untrusted checkout. Future public CLI/service routing
must preserve explicit operator selection and document this execution boundary.

The policy allows centrally installed protected binaries/configuration to be reused
across projects. It supplies neither artifact provenance nor Podman authentication,
OS containment, lease authority or a trusted-project registry. Existing final-file
replacement tests cover held-snapshot replacement; this checkpoint's new negatives
cover pre-load digest/permission rejection, not postcheck race elimination.

## Explicit CLI (checkpoint 129, unpublished)

`harness-gate --project-root /canonical/project podman-capture --trust-host
--image-id FULL_STORAGE_ID --name NAME --label owner=VALUE` explicitly executes
the mapped host's binary. `--label` may repeat with distinct keys. Optional
`--container-port` and `--host-port` must appear together; `--timeout-ms` is
1..30000 (default 3000). Empty operator labels may inherit image labels.

The project root must be explicit, absolute and canonical. The trust flag is a
statement by the invoking operator, not authentication. Missing trust/root,
invalid image/inputs/budget and duplicate labels are rejected before project
loading or socket access. This command is not invoked from doctor or verify.
Linux is required. There are no host/socket/hash/output-path overrides.

Success writes only canonical PlanRecord bytes to stdout, without a newline.
There is no implicit file persistence. On capture failure no evidence is written;
a stdout write failure can leave partial bytes and returns failure, so consumers
must require success and validate the complete record. The evidence may contain
configuration/image metadata and is not an authority token. Published protocol
and artifacts still lack this route; local pinned-source testing is separate
from a release or real Podman proof.

## Normal executable acceptance checkpoint 130

A pinned ordinary Core binary (without the joint-test feature) is invoked with
an empty environment and cwd `/` against the pinned native adapter/fake socket.
Tests require exit 0, empty stderr and exact canonical stdout without newline;
they repeat success with `--config alternate/workflow.toml`, while the host stays
at its fixed project-root location. Missing trust exits 2; missing mapped host
exits 1 with empty stdout and no socket activity, despite an arbitrary valid host
elsewhere. No evidence file is created. `/dev/full` verifies stdout write failure
returns exit 1. It is not a partial-write or blocked-pipe proof. These tests remain
local pinned-source/fake-engine acceptance, not published artifact or real Podman
acceptance.

## Partial stdout checkpoint 132

The normal-binary fake test additionally creates a 4096-byte pipe before spawn,
uses a larger valid image metadata response, reads one nonempty 4096-byte prefix,
then closes the reader. The Core stdout writer encounters a broken pipe; the test
requires exit1, a diagnostic, and refusal to decode the captured prefix as a
complete PlanRecord. This is actual partial-output/broken-pipe evidence with the
pinned normal binary. It is not proof that an indefinitely blocked consumer is
preempted, nor process containment or real-engine acceptance.

## Bounded CLI pipe output checkpoint 133

The CLI starts an overall deadline before capture and checks it again throughout
stdout emission. Linux stdout is temporarily nonblocking, with original flags
restored by a scope guard; writes poll at most 20ms between deadline/cancellation
checks. A full pipe now fails on expiry or SIGTERM/SIGINT instead of waiting for
the consumer indefinitely. Checks also run after the last successful write;
consumers must always require exit0 and validate the complete evidence.

The normal-process matrix includes a pre-sized pipe whose reader remains open
but stops draining, and signals delivered only after observed full-pipe occupancy.
The test has an independent six-second supervisor bound and kills/reaps a stuck
child before failing. These cases are distinct from EPIPE and /dev/full.

Nonblocking flags share the inherited open-file description until restored; this
is a standalone CLI output policy, not a safe library writer for arbitrary shared
stdout use. Filesystem metadata/regular-file kernel I/O and diagnostic stderr are
not forcibly preempted, and scope-guard flag restoration is best effort. No OS
containment or real-engine proof is added.

## Shared stdout flag regression checkpoint 134

The parent now retains a duplicate of the exact pipe writer passed as child fd1,
so F_GETFL observes the same open-file description. Success is checked with both
initially blocking and initially nonblocking stdout. After child exit, all flags
must equal the original value. The existing EPIPE, full-pipe timeout, SIGTERM and
SIGINT cases make the same assertion before dropping the retained writer and
draining EOF. This verifies normal/error unwinding restoration; abrupt SIGKILL,
concurrent flag changes, and restoration-system-call faults are not covered.
