# JSON Schema Catalog

This directory contains the machine-readable contracts shipped with
Harness-Gate. The schemas are versioned with the CLI and are intended for
editor validation, CI checks, and downstream integrations.

## Schemas

| File | Contract | Version and producer |
| --- | --- | --- |
| [quality.schema.json](quality.schema.json) | Optional .harness-gate/quality.toml quality intent | Generated from the Rust QualityConfig model; configuration version 1. |
| [flow.schema.json](flow.schema.json) | .harness-gate/flow.toml configuration | Generated from the Rust FlowConfig model; configuration version 2. |
| [findings-bundle.schema.json](findings-bundle.schema.json) | Completed report and source bundle for diagnostic normalization | harness-findings/1; generated by findings schema --bundle. |
| [findings.schema.json](findings.schema.json) | Normalized findings and retained diagnostic history | harness-findings/1; generated by findings schema. |
| [machine-result.schema.json](machine-result.schema.json) | test_result.json verification result | Machine result schema version 1. |
| [verification-plan.schema.json](verification-plan.schema.json) | Read-only verify --plan --json selection explanation | verification-plan/v1; always has a null verification_result. |
| [artifact-manifest.schema.json](artifact-manifest.schema.json) | Invocation artifact manifest | Manifest schema version 1. |
| [artifact-registry.schema.json](artifact-registry.schema.json) | Invocation artifact registry | Registry schema version 1. |
| [adapter-request.schema.json](adapter-request.schema.json) | Signed out-of-process adapter request | Adapter protocol version 2; result schema version 1. |
| [collector-protocol.schema.json](collector-protocol.schema.json) | Collector request/response/error envelope | Harness collector protocol version 1. |

The schemas describe structure and closed vocabularies. They do not replace
harness-gate config check, which also evaluates environment interpolation,
repository containment, cross-field references, ownership, and network policy.

## Generate and validate

Run these commands from the repository root:

    cargo run --manifest-path tools/harness-gate/Cargo.toml --locked -- \
      schema export --output schema/flow.schema.json
    cargo run --manifest-path tools/harness-gate/Cargo.toml --locked -- \
      schema export --quality
    python3 -m json.tool schema/flow.schema.json >/dev/null
    for schema in schema/*.schema.json; do
      python3 -m json.tool "$schema" >/dev/null || exit 1
    done

The flow and quality schemas are generated; do not hand-edit it. A model change must update
the Rust source, regenerate the file, and include the result in the same
change. CI compares the generated bytes with the committed file.

## Compatibility

Consumers should treat each schema version as a contract. New fields may only
be added under the project's compatibility policy; unknown fields are rejected
where the schema declares additionalProperties: false. A major semantic change
requires a new schema version and an ADR. The audit rules file has its own
migration contract; see the
[audit v2 migration section](../docs/configuration.md#audit-v2-migration).

The nested runner contract is version 2. Runner v1 requires explicit external
migration; see [ADR 0054](../docs/adr/0054-declarative-runner-inputs.md).
The enclosing flow contract remains version 2.

Invocation metadata is a separate supplemental record: `invocation.json`
declares `metadata_version: 2`; records without that field are legacy version 1.
The compatibility `toolchain` string is now `"unknown"`, and checkout `commit`
is optional context from a bounded discovery probe. The machine-result,
artifact-manifest and artifact-registry schemas stay at version 1. Tool identity
consumers should migrate to runner descriptions and bound collector evidence;
see the [metadata migration and failure semantics](../docs/configuration.md#15-reports-templates-and-notifications).

For a human-readable configuration guide, read the
[English configuration reference](../docs/configuration.md) or the
[Chinese configuration reference](../docs/configuration.zh-CN.md). The
[adapter protocol ADR](../docs/adr/0033-signed-out-of-process-adapter-protocol.md)
documents signature and capability requirements that are intentionally stricter
than the JSON shape alone.

The [quality configuration reference](../docs/quality-configuration.md) documents
collector authority, policy bindings and flow/quality cross-validation.

The [plugin lock](plugin-lock.schema.json) and [plugin manifest](plugin-manifest.schema.json)
describe data-only offline preset packages. [Plugin onboarding](../docs/plugin-lock.md)
defines exact signing bytes, host trust, compatibility checks and migration/rollback.
